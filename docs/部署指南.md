# 部署指南

本文档是本项目部署到可公网访问生产服务的完整方案，按 2026-10-12 迁移到新服务器 lisa 的实际流程编写。当前部署方式是：

```text
本地按 .dockerignore 打包源码（约 17 MB）
-> 上传服务器
-> 服务器上 docker build 构建镜像
-> Docker Compose 运行
-> Cloudflare Tunnel 提供公网入口
```

不再在本地构建镜像再上传：本地到服务器的跨境上行带宽实测只有约 1 Mbps，上传 120 MB 以上的镜像 tar 需要二十分钟以上；源码包只有约 17 MB，而服务器拉取基础镜像和 pip 依赖很快。

旧服务器（搬瓦工 Ubuntu）于 2026 年 10 月到期未续费，服务器上的 Docker 卷没有备份，运行时数据随之丢失，文章靠本地原稿恢复。备份要求见第十一节。

没有域名、只想临时用 IP 验证服务时，见 `docs/no-domain-access-notes.md`。临时 IP 访问不是正式上线方案。

## 目标架构

```text
用户浏览器
  -> https://getwiseoracle.com/
  -> Cloudflare
  -> Cloudflare Tunnel（服务器上的 cloudflared 主动出站连接）
  -> 127.0.0.1:8000
  -> Docker 容器 zhugeshensuan:<版本号>
```

关键约束：

- Docker 容器只绑定服务器本机 `127.0.0.1:8000`。
- 服务器不需要为网站开放 `80` 和 `443`；公网入口由 Cloudflare 提供。
- 不直接把 Docker 的 `8000` 端口暴露到公网。
- 服务器运行项目时不需要手动执行 `python app.py`。
- `.env` 只放在部署目录，不提交仓库，不写进镜像，不写进 Nginx 配置。
- 本仓库是公开仓库，文档中不记录服务器公网 IP；暴露源站 IP 会让访问者绕过 Cloudflare。

## 当前生产服务器 lisa

lisa 同时承担三项任务：网站源站、Tailscale 出口节点、自建 Tailscale DERP 中继（derper）。

| 项目 | 规格 |
|---|---|
| 位置 | 洛杉矶 |
| 配置 | KVM，1 vCPU，1 GB 内存，20 GB 磁盘 |
| 系统 | Ubuntu 24.04 LTS |
| 网络 | 60 Mbps 上下行端口，每月 2000 GB 流量 |
| 登录 | 通过 Tailscale：`ssh root@lisa` |

`lisa` 是 Tailscale 中的主机名，需要本机 Tailscale 启用 MagicDNS；未启用时，用 Tailscale 管理后台显示的 `100.x.x.x` 地址替换。

监听端口：

| 端口 | 服务 | 说明 |
|---|---|---|
| `22/tcp` | sshd | SSH |
| `41641/udp` | tailscaled | Tailscale 直连 |
| `8443/tcp`、`3478/udp` | derper | 自建 DERP 中继和 STUN |
| `127.0.0.1:8000` | Docker 容器 | 只供本机 cloudflared 访问 |

资源基线（2026-10-12 部署完成后实测）：

| 项目 | 占用 |
|---|---|
| 应用容器 | 约 140 MiB，Compose 限制 `mem_limit: 400m` |
| 整机可用内存 | 约 470 MB，另有 2 GB swap 兜底 |
| 磁盘剩余 | 约 12 GB |
| 流量 | 出口节点和网站合计，首 9 天进出共约 117 GB |

### 与 Tailscale 出口共存的约束

站长电脑（以及远程协作会话）通过 lisa 作为出口上网时，lisa 的任何网络中断都会让这些设备同时断网。在 lisa 上操作必须遵守：

1. **重启要预约并提前告知。** 用 `shutdown -r +2` 预约 2 分钟后重启（生效前可用 `shutdown -c` 取消），重启期间约 1–3 分钟断网。tailscaled、derper、docker、cloudflared 都已设为开机自启，网站容器随 Docker 自动恢复。
2. **apt 安装或升级时禁止自动重启服务。** Ubuntu 24.04 的 needrestart 会在 apt 结束后自动重启使用旧库的服务（包括 systemd-networkd）。命令前加 `NEEDRESTART_MODE=l`，只列出、不重启。如果 `/var/run/reboot-required` 存在（内核或 libc 已更新），先按第 1 条重启，再安装 Docker 等软件。
3. **改动转发规则前先设自动恢复定时器。** 安装 Docker 等会改 iptables 的操作，按第三节先设定时器，从出口设备验证上网正常后再取消。
4. **不要只放行 SSH 就启用 ufw。** 当前 ufw 未启用。如需启用，必须同时放行 `22/tcp`、`41641/udp`、`8443/tcp`、`3478/udp`，否则 DERP 中继会失效。
5. **出口流量计入服务器月流量。** 首 9 天合计约 117 GB，按月约 400 GB，在 2000 GB 额度内。

## 准备信息

部署前准备：

- 生产服务器，能以 root 通过 SSH 密钥登录；当前为 lisa。
- 一个 Cloudflare 托管的域名；当前域名为 `getwiseoracle.com`。
- 本地 Windows 项目目录：`V:\诸葛神算V4`，以及其中的 Python 虚拟环境 `.venv`（打包脚本只用标准库）。
- 本地不需要 Docker。

使用 Cloudflare Tunnel 时，不需要把域名 A 记录指向服务器公网 IP。Tunnel 的 Published application route 会自动配置对应 DNS 路由。

## 一、本地准备部署文件

### 1. 检查 `.env`

`.env` 必须包含：

```env
IMAGE_NAME=zhugeshensuan
IMAGE_TAG=4.1.6-analytics
APP_PORT=8000
APP_ENV=production
APP_DEBUG=false
SITE_BASE_URL=https://getwiseoracle.com
CONTACT_EMAIL=5siwei@gmail.com
ARTICLE_ADMIN_PATH=165131
ARTICLE_ADMIN_PASSWORD=设置一个只由站长知道的访问密码
TRUSTED_PROXY_HOPS=1
SECRET_KEY=替换为生产密钥
AI_API_KEY=替换为模型供应商密钥
AI_BASE_URL=https://api.deepseek.com
AI_MODEL=deepseek-flash
AI_GLOBAL_DAILY_LIMIT=100
```

`IMAGE_TAG` 必须与第五节构建的镜像标签一致；本地 `.env` 里的值可以不改，上传后在服务器上修改（第六节）。

`AI_MODEL` 使用 DeepSeek 模型列表中的正式名称。2026-10-12 核对时，列表只有 `deepseek-flash` 和 `deepseek-v4-pro`；旧名称 `deepseek-v4-flash` 不在列表中，但调用时仍作为别名由 `deepseek-flash` 提供服务。代码、`deploy/compose.prod.yml` 和 `.env.example` 的默认值已统一为 `deepseek-flash`。更换模型前先在服务器上确认：

```bash
cd ~/zhugeshensuan
curl -s https://api.deepseek.com/models -H "Authorization: Bearer $(grep '^AI_API_KEY=' .env | cut -d= -f2-)"
```

`SITE_BASE_URL` 是 canonical、hreflang、Open Graph、JSON-LD、sitemap 和 robots 使用的唯一生产 origin。生产值必须是公开 HTTPS 根地址，不带路径、查询参数或末尾斜杠；应用不会根据请求 `Host` 或代理转发的 host 动态生成 SEO URL。测试/预发布环境必须显式使用各自的 `SITE_BASE_URL`，不得让预发布域名写入正式页面源码。

`CONTACT_EMAIL` 是 Contact、Privacy、Terms 和 Disclaimer 统一公开的联系邮箱。生产环境必须显式配置有效的公开邮箱；空值、无效格式和 `.example` 占位域名都会导致应用拒绝启动。

`ARTICLE_ADMIN_PATH=165131` 形成私密文章入口 `https://getwiseoracle.com/165131`。它必须是 6 位数字；以后修改该环境变量并重启容器即可让旧 URL 失效。`ARTICLE_ADMIN_PASSWORD` 是这个页面的简单访问密码；留空时只依赖 URL 后缀，上传功能仍可用。

`TRUSTED_PROXY_HOPS=1` 已在 lisa 上验证：cloudflared 转给应用的 `X-Forwarded-For` 只有一个值，即 Cloudflare 看到的访客 IP，应用据此做每 IP 的 AI 限额。

`docker compose --env-file .env` 只为 Compose 提供变量替换；`deploy/compose.prod.yml` 已在容器 `environment` 中显式传递公开配置、文章入口配置，并把文章目录固定为持久卷内的 `/app/content/articles_en`。

不要把 `.env` 发到 GitHub，也不要截图外发。

## 二、初始化服务器

本节记录 lisa 上实际执行过的初始化。lisa 已经完成，只有换新服务器时才需要重做。

登录服务器：

```powershell
ssh root@lisa
```

### 1. 更新系统

```bash
export NEEDRESTART_MODE=l
apt update
apt upgrade -y
ls /var/run/reboot-required 2>/dev/null && cat /var/run/reboot-required.pkgs
```

如果存在 `reboot-required`，按“与 Tailscale 出口共存的约束”第 1 条预约重启，恢复后再继续。

### 2. 添加 swap

1 GB 内存同时运行 Tailscale 出口、derper、Docker 和网站，必须有 swap 兜底：

```bash
cp -a /etc/fstab /etc/fstab.bak-$(date +%Y%m%d)
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
echo 'vm.swappiness=10' > /etc/sysctl.d/99-swappiness.conf
sysctl -p /etc/sysctl.d/99-swappiness.conf
systemctl daemon-reload
swapon --show
```

### 3. 限制日志并停用不需要的服务

```bash
mkdir -p /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=100M\nRuntimeMaxUse=30M\n' > /etc/systemd/journald.conf.d/50-size-limit.conf
systemctl restart systemd-journald
journalctl --disk-usage
```

确认 snap 中没有在用的软件（lisa 上只有从未初始化过的 lxd）、系统盘不是多路径设备后，停用 snapd 和 multipathd：

```bash
snap list
lsblk
systemctl disable --now snapd.service snapd.socket snapd.seeded.service
systemctl disable --now multipathd.service multipathd.socket
```

### 4. Tailscale 出口转发优化

Tailscale 建议出口节点开启网卡的 UDP GRO 转发。lisa 的默认网卡是 `ens17`，换服务器时用 `ip route show default` 确认网卡名：

```bash
ethtool -K ens17 rx-udp-gro-forwarding on rx-gro-list off
cat > /etc/systemd/system/tailscale-udp-gro.service <<'UNIT'
[Unit]
Description=Enable UDP GRO forwarding on ens17 for Tailscale exit node
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/sbin/ethtool -K ens17 rx-udp-gro-forwarding on rx-gro-list off

[Install]
WantedBy=multi-user.target
UNIT
systemctl daemon-reload
systemctl enable --now tailscale-udp-gro.service
ethtool -k ens17 | grep -E 'rx-udp-gro-forwarding|rx-gro-list'
```

这是一次性服务，`systemctl status` 显示 `inactive` 是正常的；以 `ethtool -k` 显示 `rx-udp-gro-forwarding: on` 为准。

### 5. 防火墙

lisa 当前不启用 ufw。Cloudflare Tunnel 由服务器主动出站连接 Cloudflare，网站不需要任何入站端口。如需启用 ufw，必须先放行 Tailscale 和 derper：

```bash
ufw allow 22/tcp
ufw allow 41641/udp
ufw allow 8443/tcp
ufw allow 3478/udp
ufw enable
```

## 三、安装 Docker

使用 Docker 官方 apt 仓库安装 Docker Engine 和 Compose。lisa 是出口节点，先设自动恢复定时器：5 分钟后自动把转发策略恢复为接受，防止出口断网后无法远程处理：

```bash
systemd-run --unit=forward-failsafe --on-active=300 /bin/sh -c 'iptables -P FORWARD ACCEPT; ip6tables -P FORWARD ACCEPT'
```

添加仓库并写入日志限制：

```bash
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  tee /etc/apt/sources.list.d/docker.list > /dev/null

mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'JSON'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
JSON
```

`daemon.json` 限制容器日志为 10 MB × 3 个文件，防止 gunicorn 访问日志占满磁盘。

安装：

```bash
apt update
NEEDRESTART_MODE=l apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
docker version
docker compose version
iptables -S FORWARD
```

`iptables -S FORWARD` 中必须仍有 `-A FORWARD -j ts-forward`。本次实测 Docker 29.9.0、Compose v5.6.0；由于 Tailscale 已开启 IP 转发，Docker 没有把 FORWARD 默认策略改为 DROP。

在通过 lisa 出口上网的设备上确认出口正常（显示的应是 lisa 的公网 IP）：

```powershell
curl.exe -s https://ipinfo.io/ip
```

确认正常后取消定时器：

```bash
systemctl stop forward-failsafe.timer
```

## 七、配置 Cloudflare Tunnel

源站容器只监听服务器本机 `127.0.0.1:8000`。Cloudflare Tunnel 把公网域名请求转发到这个本机地址，不需要暴露源站 IP。

### 1. 安装 cloudflared

```bash
mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-public-v2.gpg | tee /usr/share/keyrings/cloudflare-public-v2.gpg >/dev/null
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-public-v2.gpg] https://pkg.cloudflare.com/cloudflared any main' | tee /etc/apt/sources.list.d/cloudflared.list
apt-get update && NEEDRESTART_MODE=l apt-get install -y cloudflared
cloudflared --version
```

本次实测版本：

```text
cloudflared version 2026.10.0
```

`cloudflared service install` 安装的服务带 `--no-autoupdate`，Cloudflare 的软件源也不在 Ubuntu 自动安全更新范围内。需要定期手动更新：

```bash
NEEDRESTART_MODE=l apt-get install --only-upgrade -y cloudflared
systemctl restart cloudflared
```

### 2. 迁移到新服务器：复用原 Tunnel

2026-10-12 迁移到 lisa 时采用这种方式。域名路由不用改，只需把连接器换到新服务器：

1. 打开 `https://one.dash.cloudflare.com/`，进入 `Networks -> Connectors`，打开原 Tunnel `zhugeshensuan`。旧服务器下线后它显示为 Down，网站返回 530。
2. 在 Tunnel 配置页的连接器安装页面选择 `Debian`、`64-bit`，复制带令牌的安装命令。
3. 在新服务器以 root 执行（不需要 `sudo`）：

```bash
cloudflared service install <页面给出的token>
```

令牌保存在 `/etc/cloudflared/token`，不会出现在进程参数中。不要使用只在当前终端临时运行的 `cloudflared tunnel run --token <token>`。

检查服务：

```bash
systemctl status cloudflared --no-pager
journalctl -u cloudflared -n 30 --no-pager
```

日志应出现 4 条 `Registered tunnel connection ... protocol=quic`，以及包含 `getwiseoracle.com` 和 `www.getwiseoracle.com` 到 `http://127.0.0.1:8000` 的 `Updated to new configuration`。`ICMP proxy feature is disabled` 警告只影响 WARP 的 ICMP 转发，本项目未使用，可以忽略。控制台中 Tunnel 状态应变为 `HEALTHY`。

### 3. 首次部署：新建 Tunnel

只有没有可复用的 Tunnel 时才需要本节。

进入 `https://one.dash.cloudflare.com/`。如果第一次启用 Zero Trust：选择 Free 计划，点击 `Continue to Zero Trust`；如果跳转 404，手动重新打开该地址。

依次打开：

```text
Networks -> Connectors -> Add a tunnel
```

Tunnel 类型选择 `Cloudflared`，名称建议 `zhugeshensuan`，操作系统选择 `Debian`、`64-bit`（Ubuntu 属于 Debian 系）。按第 2 小节的方法在服务器执行页面给出的 `cloudflared service install <token>`。

然后在 Tunnel 详情页打开：

```text
Published application routes -> Add a published application route
```

根域名访问 `https://getwiseoracle.com/`，填写：

```text
Subdomain: 留空
Domain: getwiseoracle.com
Path: 留空
Service Type: HTTP
URL: 127.0.0.1:8000
```

注意：

- `Subdomain` 不要填 `https://getwiseoracle.com`。
- 页面应显示 `Full hostname: getwiseoracle.com`。
- `Type` 选择 `HTTP` 后，`URL` 只填 `127.0.0.1:8000`，不要再写 `http://`。

### 4. HTTPS 强制跳转

在 Cloudflare 主控制台（不是 Zero Trust 控制台）进入：

```text
getwiseoracle.com -> SSL/TLS -> Edge Certificates
```

开启 `Always Use HTTPS`。开启后 `http://getwiseoracle.com/` 会 301 跳转到 `https://getwiseoracle.com/`。

### 5. www 域名跳转到裸域名

当前使用裸域名 `https://getwiseoracle.com/` 作为唯一主域名，`www` 永久跳转到裸域名，避免重复页面、集中索引信号。

先在 Tunnel 中为 `www` 添加一条 Published application route：

```text
Subdomain: www
Domain: getwiseoracle.com
Path: 留空
Service Type: HTTP
URL: 127.0.0.1:8000
```

再在 Cloudflare 主控制台添加 Page Rule：

```text
getwiseoracle.com -> Rules -> Page Rules -> Create Page Rule
URL: www.getwiseoracle.com/*
Setting: Forwarding URL
Status Code: 301 - Permanent Redirect
Destination URL: https://getwiseoracle.com/$1
```

不要再添加 `getwiseoracle.com/* -> ...` 的跳转规则，否则容易造成循环跳转。`http -> https` 已由 `Always Use HTTPS` 负责，不需要额外写 Page Rule。

DNS 未生效时，可用公共 DNS 检查并刷新本机缓存：

```powershell
nslookup -type=A www.getwiseoracle.com 1.1.1.1
ipconfig /flushdns
```

## 十一、备份与恢复

运行时数据库在 Docker 卷 `zhugeshensuan_runtime-data` 中，对应容器内 `/app/instance`；上传的 Markdown 文章在 `zhugeshensuan_article-content` 中，对应 `/app/content/articles_en`。两者都必须备份，而且**备份必须下载到服务器以外**：备份只留在服务器上，服务器到期或损坏时会和数据一起丢失，旧服务器就是这样丢的数据。管理页面的“打包下载全部文章”可随时导出全部 `.md`，但不代替卷备份。详细演练步骤见 `docs/operations/backup-restore-runbook.md`。

docker run --rm -v zhugeshensuan_runtime-data:/data -v "$PWD/backups:/backup" alpine \
  cp /data/runtime.db /backup/runtime-$(date +%Y%m%d-%H%M%S).db
docker run --rm -v zhugeshensuan_article-content:/data:ro -v "$PWD/backups:/backup" alpine \

下载到本地：

```powershell

```

`instance/` 已被 `.gitignore` 和 `.dockerignore` 排除，备份不会进入仓库或镜像。

恢复时先停止应用：数据库备份恢复为 runtime 卷内 `/data/runtime.db`；文章压缩包解压到 article-content 卷根目录并确认存在 `/data/articles_en/*.md`。随后启动应用，检查 `/readyz`、`/articles` 和一篇文章详情。只有文章原稿而没有卷备份时，按第八节恢复。恢复演练必须先在非生产环境完成。

## 常见问题与处理

### 1. `failed to read dockerfile: open Dockerfile: no such file or directory`

现象：

```text
Image zhugeshensuan:4.1 Building
failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory
```

原因：

- 启动命令漏了 `--no-build`，Compose 尝试在没有源码的部署目录上一级构建镜像。
- 服务器上没有 `.env` 中 `IMAGE_TAG` 对应的镜像，或启动命令没有带 `--env-file .env`，Compose 退回默认镜像 `zhugeshensuan:4.1`。

处理：

```bash
cd ~/zhugeshensuan
docker images zhugeshensuan
grep -E '^(IMAGE_NAME|IMAGE_TAG|APP_PORT|AI_MODEL)=' .env
docker compose --env-file .env -f compose.prod.yml up -d --no-build --force-recreate
```

`IMAGE_TAG` 必须是 `docker images zhugeshensuan` 中存在的标签。

### 2. `invalid reference format` 或配置值末尾多出 `\r`

原因：`.env` 或 `compose.prod.yml` 从 Windows 上传后带有 CRLF 换行。

处理：

```bash
cd ~/zhugeshensuan
sed -i 's/\r$//' .env compose.prod.yml
docker compose --env-file .env -f compose.prod.yml up -d --no-build --force-recreate
```

### 3. `docker compose ps` 没有容器

原因：容器没有成功创建，前一步 `up` 失败。

处理：

```bash
cd ~/zhugeshensuan
docker compose --env-file .env -f compose.prod.yml up -d --no-build
docker compose --env-file .env -f compose.prod.yml logs --tail=100 app
docker compose --env-file .env -f compose.prod.yml ps
```

### 4. `curl 127.0.0.1:8000/readyz` 失败

现象：

```text
curl: (7) Failed to connect to 127.0.0.1 port 8000
```

原因：

- 容器未启动。
- 容器启动后健康检查失败。
- 端口没有绑定到服务器本机。

处理：

```bash
docker compose --env-file .env -f compose.prod.yml ps
docker compose --env-file .env -f compose.prod.yml logs --tail=100 app
ss -lntp | grep ':8000'
```

`/readyz` 返回 503 时，响应中的 `checks` 字段会列出失败项，例如 `AI_API_KEY`、`ARTICLE_CONTENT`。

### 5. 浏览器访问 `http://服务器IP:8000` 失败

这是当前生产配置下的预期行为。`compose.prod.yml` 只绑定 `127.0.0.1:8000->8000`，只有服务器本机能访问，公网不能直接访问 `服务器IP:8000`。正式访问应通过 Cloudflare Tunnel 访问域名。

如果没有域名，仅做临时 IP 验证，见 `docs/no-domain-access-notes.md`。

### 6. Cloudflare Tunnel 状态不是 HEALTHY

先检查服务器服务：

```bash
systemctl status cloudflared --no-pager
journalctl -u cloudflared -n 50 --no-pager
```

如果日志中能看到 `Environment is healthy`，但随后反复出现 `control stream encountered a failure while serving` 和 `Retrying connection`，先回到 Cloudflare 控制台查看 Tunnel 状态。如果控制台显示 `HEALTHY`，通常可以继续；如果显示 `Disconnected` 或 `Unhealthy`，再考虑切换协议或重装 connector。

### 7. 域名访问失败或返回 530

按顺序检查：

```bash
curl --fail http://127.0.0.1:8000/readyz
systemctl status cloudflared --no-pager
journalctl -u cloudflared -n 50 --no-pager
curl -I https://getwiseoracle.com
```

如果本机 `127.0.0.1:8000/readyz` 正常，但域名不正常，问题通常在 Cloudflare Tunnel、Published application route 或 Cloudflare DNS 路由，不在 Docker 容器。返回 530 通常表示 Tunnel 没有健康的连接器，例如旧服务器下线后新服务器还没安装连接器。

### 8. Published application route 填错

根域名不要填在 `Subdomain` 里。错误示例：

```text
Subdomain: https://getwiseoracle.com
Domain: getwiseoracle.com
Full hostname: https://getwiseoracle.com.getwiseoracle.com
```

正确示例：

```text
Subdomain: 留空
Domain: getwiseoracle.com
Full hostname: getwiseoracle.com
Type: HTTP
URL: 127.0.0.1:8000
```

### 9. 安装或升级 Docker 后，经 lisa 出口的设备断网

原因：Docker 把 FORWARD 默认策略改成了 DROP，且 Tailscale 的 `ts-forward` 规则没有放行出口流量。

处理：等第三节设的定时器自动恢复（5 分钟内），或通过 Tailscale SSH 登录 lisa（SSH 走入站规则，不受转发规则影响）立即恢复：

```bash
iptables -P FORWARD ACCEPT
ip6tables -P FORWARD ACCEPT
iptables -S FORWARD
```

`iptables -S FORWARD` 中必须有 `-A FORWARD -j ts-forward`；没有时执行 `systemctl restart tailscaled`，这会让出口再中断几秒。

### 10. 打包脚本提示“拒绝打包”

原因：`.env`、Google OAuth 客户端密钥、Cloudflare 令牌等凭据文件进入了构建上下文。

处理：在 `.dockerignore` 中排除提示的文件后重新打包。不要删除脚本中的检查；凭据一旦进入镜像，任何拿到镜像的人都能读取。

### 11. 论命请求失败，日志显示模型不存在

原因：`.env` 的 `AI_MODEL` 不是模型供应商当前可用的模型名（旧名称作为别名时可能仍可调用，但别名随时可能下线）。

处理：按第一节查询可用模型，修改服务器 `.env` 的 `AI_MODEL`，然后重建容器。

### 12. 传统 Nginx/Certbot 方案什么时候使用

只有不使用 Cloudflare Tunnel、让域名直接解析到服务器公网 IP 时，才需要在服务器开放 `80/443`、配置 Nginx、申请 Certbot 证书。lisa 的 `443` 端口目前空闲，但继续推荐 Cloudflare Tunnel：源站 IP 不暴露，也不需要任何入站端口。
